## 1. Purpose

This document addresses data handling practices, privacy posture, and regulatory applicability for Grant Opportunity Matcher. It is intended for compliance teams, legal counsel, and technical program managers conducting risk assessments or procurement reviews.

---

## 2. Data Inventory

### 2.1 Data Processed by the Application

| Data Type | Source | Sensitivity | Persistence | Transmitted To |
|---|---|---|---|---|
| Nonprofit profile (name, mission, focus areas, populations, location, programs) | User input (operator) | **Low–Medium** | Session-only (in-memory) | AI provider (optional, sanitized) |
| Grant opportunity data (title, agency, description, award amounts, deadlines) | Grants.gov public API | **Public** | Session-only (cached max 5 min) | Not transmitted externally |
| AI provider API key | Environment variable | **High** | Environment only (never written to disk by the app) | Provider API (in Authorization header) |
| AI scoring response (score + rationale) | AI provider API | **Low** | Session-only | Not transmitted |
| Exported CSV / Markdown report | Generated by the app | **Low–Medium** | User's local filesystem only | Not transmitted |

### 2.2 Data NOT Collected or Stored

The application does **not** collect, store, or transmit:

- Personal Identifiable Information (PII) of grant applicants or beneficiaries
- Financial account information
- Health information (PHI)
- Authentication credentials for application users
- Usage analytics or telemetry (Streamlit usage stats are disabled via `config.toml`)
- Session logs containing user inputs

## 3. Data Flows and Third-Party Disclosure

### 3.1 Grants.gov (Federal API)

- **Data sent:** Keyword query string derived from the operator-entered profile (mission, focus areas, programs). No PII is included in this query.
- **Data received:** Publicly available federal grant opportunity data.
- **Legal basis:** Public API; no data processing agreement required.
- **Retention by third party:** Not applicable — query is stateless; Grants.gov logs API access at the server level per federal policy.

### 3.2 AI Providers (Optional)

If AI scoring is enabled, the following data is transmitted to the configured provider in a single API request per grant evaluated:

- A sanitized profile summary (organization name, mission, focus areas, populations, location, tax status, programs, target award range)
- A sanitized grant record (title, agency, award range, deadline, categories, eligible applicants, description)

**No free-text user data beyond the operator's own organizational profile is transmitted.** The profile is entered by the operator for the explicit purpose of grant matching.

| Provider | Privacy Policy | Data Retention |
|---|---|---|
| Anthropic | [anthropic.com/privacy](https://www.anthropic.com/privacy) | Per Anthropic API terms |
| OpenAI | [openai.com/policies/privacy-policy](https://openai.com/policies/privacy-policy) | Per OpenAI API terms |
| Groq | [groq.com/privacy](https://groq.com/privacy) | Per Groq API terms |
| Ollama (local) | N/A — data never leaves the local host | No external transmission |

**Recommendation:** For deployments where the nonprofit's mission statement or service population descriptions may be considered sensitive organizational intelligence, prefer the Ollama (local) provider to ensure no profile data leaves the operator's environment.

## 4. Regulatory Applicability Assessment

### 4.1 GDPR / CCPA

**Applicability: Low**

The application does not process personal data of natural persons in the ordinary course of its operation. The nonprofit profile describes an organization, not an individual. No PII of beneficiaries, clients, or staff is entered into or processed by the application.

If an operator enters an individual's name or contact information into a profile field (e.g., as part of the mission statement), that would be operator error outside the intended use case. The application has no mechanism to detect or prevent this.

**Action item:** Include a note in operator onboarding that profile fields should contain organizational descriptors, not individual identifying information.

### 4.2 HIPAA

**Applicability: None**

The application does not process Protected Health Information (PHI). While some grant categories relate to health services (mental health, substance use treatment), the grant data itself is public federal records, not patient data.

### 4.3 FedRAMP / FISMA

**Applicability: Conditional**

If deployed within a federal agency environment or used to process federal program data on behalf of a government entity, FedRAMP authorization of the hosting platform may be required. The application itself does not handle Controlled Unclassified Information (CUI).

- **Grants.gov API:** A publicly accessible federal API; use does not trigger FedRAMP requirements.
- **AI Provider:** Anthropic, OpenAI, and Groq do not currently hold FedRAMP authorization for their commercial APIs. For federal deployments requiring FedRAMP compliance, use the Ollama (local) provider to avoid transmitting any data to non-FedRAMP-authorized services.

### 4.4 SOC 2

**Applicability: Conditional**

If the application is deployed as part of a service offered to external customers, the operator's SOC 2 program should account for:

- **Availability:** Dependency on Grants.gov API uptime (mitigated by demo data fallback)
- **Confidentiality:** Nonprofit profile data in-session and in export files
- **Processing Integrity:** Accuracy of keyword and AI scoring results

The application's in-memory-only data model simplifies SOC 2 evidence collection — there is no database, no audit log store, and no persistent user data to review.

## 5. AI/ML-Specific Compliance Notes

### 5.1 Model Output Reliability

AI relevance scores are provided as **decision-support information**, not authoritative grant eligibility determinations. The application's UI labels these as "AI relevance scoring" and presents them alongside keyword scores and raw grant descriptions so operators can apply their own judgment.

**Recommended disclosure to end users:** Include a statement in operator training materials that AI scores reflect model judgment and should be verified against original Grants.gov listings before any application decisions are made.

### 5.2 Prompt Injection and Data Integrity

Grants.gov grant descriptions are externally-sourced data. There is a theoretical risk that a malicious actor could embed adversarial content in a grant description to manipulate AI scoring output. The application implements prompt sanitization controls (see [Security Controls](./security-controls.md) §3.2) to mitigate this risk, but no control is absolute.

**Residual risk:** An adversarially crafted grant description could influence AI scoring output. Operators should treat AI scores as one signal among several and verify high-priority matches against the Grants.gov source directly.

### 5.3 Model Version Pinning

AI provider models are pinned to specific versions in the source code to prevent silent behavioral changes from provider alias updates:

| Provider | Pinned Model |
|---|---|
| Anthropic | `claude-haiku-4-5-20251001` |
| OpenAI | `gpt-4o-mini-2024-07-18` |
| Groq | `llama-3.1-8b-instant` |
| Ollama | `llama3.2` |

Operators can override via the `AI_MODEL` environment variable. Any override should be tested before production use, as model changes may affect output format parsing.

## 6. Data Retention and Disposal

| Data Category | Retention | Disposal Mechanism |
|---|---|---|
| Session data (profile, grant results, scores) | Duration of Streamlit session only | Cleared automatically on session close or server restart |
| Streamlit cache (grant API results) | Maximum 5 minutes (`TTL=300s`) | Automatically expired by Streamlit cache engine |
| API keys | Environment variable lifetime | Cleared when the process exits; no disk write |
| Exported files (CSV, Markdown) | Operator's local filesystem | Operator is responsible for retention and disposal per their own policy |

The application does not implement any data retention controls for exported files. If exported reports contain sensitive organizational information, operators should apply their own document retention and disposal policies.

## 7. Change Management Considerations

Any of the following changes should trigger a compliance review before deployment:

| Change Type | Review Required |
|---|---|
| Addition of user authentication | Identity & access management review |
| Addition of a database or persistent data store | Data residency, retention, and access control review |
| Change to AI provider (new vendor) | Third-party vendor assessment; update §3.2 |
| Deployment in a federal environment | FedRAMP applicability assessment |
| Addition of PII fields to the profile model | GDPR/CCPA impact assessment |
| Export of data to a third-party system | Data processing agreement review |
| Multi-tenancy support | Tenant isolation and access control review |
